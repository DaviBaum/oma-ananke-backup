[26689] 116. Oma in Plain English
[26690] Oma is a building compiler.
[26691] A reasoning model can read design intent, query the project, and propose architecture, equipment, topology, routing, or lifecycle changes through typed tools. Those proposals do not directly become the building. They are checked against a persistent semantic project state, validated as transactions, routed and optimized through specialized systems, and committed only as new immutable project roots.
[26692] Each accepted root records exactly what changed, what was reused, what was invalidated, which proofs apply, which assumptions remain, and what is still UNKNOWN. The router, optimizers, AI model, GPU kernels, viewer, and exporters can be replaced without changing what a valid certificate means, provided their outputs continue to pass the same independent validators.
[26693] The first implementation remains a bounded research compiler built on the existing Oma and Concordia-Lite code. The complete PCSIR–PCROUTE–PCJCD–PCDYN–PCOMA architecture defined here is the target system, not a claim that every component already exists.

[26714] The state law is:
[26715] \[ \boxed{ \textbf{ Oma has one authoritative semantic project lineage. Every accepted mutation moves that lineage from one closed canonical root to another through a validated transaction. } } \]
[26716] The compiler law is:
[26717] \[ \boxed{ \textbf{ Generation and optimization may be sophisticated and untrusted. Released transformations are accepted only through independently checkable relations. } } \]
[26718] The MCP law is:
[26719] \[ \boxed{ \textbf{ The architecture MCP exposes typed, effect-declared, capability-controlled operations over the compiler. It does not give an AI ownership of project truth. } } \]
[26720] The authority law is:
[26721] \boxed{ \textbf{ Permission to alter a building and proof that the alteration is valid are orthogonal. Oma requires both. }
[26722] The package law is:
[26723] \[ \boxed{ \textbf{ PCSIR, PCROUTE, PCJCD, and PCDYN become final evidence only when their identities, versions, assumptions, scopes, and witnesses glue into one compatible project. } } \]
[26724] The release law is:
[26725] \boxed{ \textbf{ No compiler result may be released at a modality stronger than its complete proof and premise closure supports. }
[26726] The incremental law is:
[26727] \boxed{ \textbf{ Reuse is licensed by semantic dependency and applicability proofs—not by nearby filenames, equal display labels, or visually similar geometry. }
[26728] The viewer law is:
[26729] \boxed{ \textbf{ The viewer explains a committed building root. It never silently becomes that root. }
[26730] The AI law is:
[26731] \boxed{ \textbf{ The model proposes what should be tried. Independent validators determine what the resulting artifact proves. }
[26732] The local-runtime law is:
[26733] \boxed{ \textbf{ Project ownership, canonical state, checkpoints, and proof validity remain local to the declared workstation. Hosted intelligence is an accelerator, not a prerequisite for truth or ownership. }
[26734] The constitutional law is:
[26735] \[ \boxed{ \begin{aligned} &\textbf{Do not claim more than the witness proves.}\\ &\textbf{Do not forget what the witness assumes.}\\ &\textbf{Do not strengthen what the modality does not support.}\\ &\textbf{Do not hide what remains UNKNOWN.} \end{aligned} } \]
[26736] The final principle of the five-prompt program is:
[26737] \boxed{ \begin{minipage}{0.92\linewidth} Oma is not an LLM attached to CAD, and it is not a collection of unrelated engineering optimizers. It is a proof-carrying building compiler. Intent enters through an AI semantic front end, but authoritative state lives in a persistent, typed, spatial, operational, and lifecycle representation. Every proposed architectural, structural, equipment, topology, routing, or policy change is a transaction against an immutable project root. PCSIR establishes what the building means. PCROUTE establishes how its physical systems can occupy space. PCJCD lets architecture and routing change one another through mathematically valid feedback. PCDYN extends the physical system through construction, commissioning, operation, uncertainty, failure, maintenance, retrofit, external coupling, and lifecycle. The architecture MCP exposes this compiler through typed, capability-controlled tools. Search systems, models, GPU kernels, importers, optimizers, and viewers remain replaceable and largely untrusted. A minimized independent kernel checks their outputs, composes compatible proof packages, preserves versions and assumptions, rejects stale or contradictory artifacts, and releases only the exact modality supported by one globally coherent witness. The result is not merely a drawing, route set, BIM model, simulation, or AI answer. It is one persistent, versioned, transactional, executable, incrementally recertifiable, proof-carrying physical building system. \end{minipage} }
